# 基于真实 Obsidian 样本的分块设计与审阅记录

更新：2026-10-28（Asia/Shanghai）。状态：真实样本只读审阅完成，v2 设计已记录，并提供文档中的五脚本参考实现；尚未在项目根落地脚本、生成真实 chunks、计算 embedding 或验收真实检索效果。

本文件回答“针对我的笔记，该如何自动分块”。它记录设计依据和样本证据，当前完整操作入口是 [OBSIDIAN_RAG_V2_GUIDE.md](OBSIDIAN_RAG_V2_GUIDE.md)，含首次建库与频繁新增笔记的增量同步。原 [OBSIDIAN_RAG_GUIDE.md](OBSIDIAN_RAG_GUIDE.md) 保留 v1 对照。进度见 [HANDOFF.md](../HANDOFF.md)。

## 1. 结论与证据强度

我建议采用：**先识别和整理实际内容格式，再把有理解依赖的内容组成局部单元，生成较小的检索块；命中后按关系取回必要上下文。**

最重要的变化不是把 320 改成另一个数字。实际样本表明，以下工作先于调长度：

1. 排除空模板、占位正文和不提供正文知识的动态汇总。
2. 从长 URL、HTML/CSS 等内容中分离真正可检索的文字。
3. 保持“条件—操作—结果”“正确—错误—解释”“前提—现象—结论”的关系。
4. 区分正文、代码、表格、任务、未决问题、引用/粘贴记录与链接。
5. 保留可核对的原文位置，避免将历史或引用内容直接当成当前已验证事实。
6. 对样本中实际出现的认证或个人敏感字段，在索引派生文本和回取上下文两条路径上都处理。

这是基于样本的首选实现路线。还不能称为全库最优方案：没有跑过真实分块、token 分布、检索对照或问答评估，也没有用这些样本实测 CPU 性能。规则和参数需要在下一阶段验证。

## 3. 实际发现，以及它们如何影响设计

下面的 S 编号对应附录中的文件与已读行范围。这里只记录结构证据和工程含义，不复制私人笔记全文、认证值或个人敏感值；也不核验这些笔记中技术方法当前是否正确。

| 实际现象 | 样本证据 | 对分块的影响 |
| --- | --- | --- |
| 日记只有空的通用标题，没有正文 | S01 | 不能把模板标题做成向量，否则会返回没有知识的 hits |
| 极短笔记只是占位词；另一些极短笔记有少量真实术语 | S18、S41 | 不能按“少于 N 字”统一删除，要区分占位与信息稀薄的真实记录 |
| 一篇短笔记包含完整的概念对比 | S19 | 短而完整时整篇保留，不因空行拆散比较对象 |
| 日记中存在多个不相关话题，却都归于“笔记”等通用标题 | S03、S09、S14、S15、S16 | 通用标题只记录出处，不能作为整节同主题的证据 |
| 同一任务含计划/完成日期，和文件日期不同 | S02、S25 | 任务及子项关联保留；多个日期单独记录，不混成事件日期 |
| 未决问题、删除线、修正和撤回的观点混在正文中 | S05、S11 | 不能把删去的说法或提问当作确定结论；保留状态与上下文 |
| 日记内有长代码，围栏带 title= 等信息 | S07、S09、S28 | 保存代码块标识和语言提示；长代码按结构拆，不能切成任意字符片 |
| 解释、代码、输出、正确/错误例子被空行隔开 | S24、S27、S29、S32、S33 | 空行只是候选边界，相关解释与示例需要组成局部单元 |
| 代码围栏嵌套/闭合不规范，代码语言提示和实际内容不一定一致 | S24、S29、S31、S33 | 不能假定所有笔记是规范 Markdown 或所有 python 都能 AST 解析；需要诊断和兜底 |

| 普通说明混有行内 font 等 HTML；另有真正需要保留的 XML 示例 | S03、S27、S30、S42 | 不能用统一删除 HTML 标签的正则处理全部内容 |
| 剪藏 Markdown 的长链接参数远长于可见文字 | S39，尤其 L71 的局部 | embedding 使用链接可见文字；原始长 URL 不应占满输入预算 |
| frontmatter 的 title 与文件名/正文主题不一致；来源可能是聊天记录 | S37 | 不无条件采用 YAML title，更不能把所有剪藏当作已核验文章 |
| 表格条目是相互独立的词语/缩写解释 | S23 | 以条目或小组为单位，带列标题，避免一个向量混合大量不同词语 |
| 纯链接笔记、外部文件引用、代码文件嵌入 | S20、S12、S30 | 保留引用关系；不宣称只有链接名就已索引目标内容，不自动读取范围外文件 |
| 说明主要依赖截图，文字只提供局部提示 | S06 | 记录覆盖缺口；未做 OCR 时不能回答图片中的具体设置 |
| 动态汇总文件主要是 Dataview 查询定义 | S17 | 默认不把查询当成已汇总的任务正文；任务从源日记获取 |

## 4. 建议的数据处理顺序

```text
用户明确选择的文件
  → 识别格式、范围和明显的非正文内容
  → 解析结构，保留源位置，发现异常则标记
  → 生成可检索的安全文本视图
  → 按理解依赖组成局部上下文单元
  → 对过长单元生成检索子块
  → 只为检索子块计算向量，保存关联关系
  → 命中子块后取回受预算限制的相关上下文
```

所有处理在派生视图进行，不修改源笔记。流程由程序自动执行，用户只抽查结果和异常，不逐篇人工分块。

### 4.1 文档格式与可索引内容

第一步先确定内容属于哪一种：

- 常规 Markdown：解析标题、段落、列表、代码、表格、引用与行内链接。
- 整页 HTML：要求有明确文档级标记，例如 doctype/html/body 组合；抽取 body 中标题、段落、列表、表格、pre/code，丢弃样式与脚本内容，不执行或浏览渲染。
- HTML/XML 代码示例：受代码块保护，标签是知识内容的一部分，不能当页面清洗掉。
- frontmatter：作为元数据独立解析，保留 tags、aliases、created、source 等已有字段；字段缺失/异常不猜测补全。
- 空模板或明确占位：不创建 dense chunk，给出原因。
- 纯引用、图片依赖、插件查询：记录类型与未覆盖范围，不伪造目标内容。

不采用“清洗后少于 50 字就删除”这类统一规则。S19 的短笔记是完整对比；S41 虽内容很少，仍可供精确查词，但不足以支持扩展回答。S18 的完整占位正文可以标记为占位。判断不明确时保留诊断，避免静默删除。

### 4.2 可检索文本与原文分开

建议保留三层含义：

| 层 | 用途 | 处理 |
| --- | --- | --- |
| 源笔记 | 用户原始资料 | 不修改；用相对路径、哈希、原始位置定位 |
| 检索文本 | embedding 与关键词匹配 | 去除格式噪声，保留语义、代码、状态，处理敏感值 |
| 引用/上下文文本 | 展示与生成依据 | 可阅读的源内容视图，同样应用敏感值处理，附源位置 |

关键规则：

- Markdown 链接保留可见文字，链接目标另存为经过筛查的引用信息；不把长查询参数拼进 embedding。
- wikilink 保留显示名/目标名和目标片段关系；不要将未解析的目标名冒充目标正文。
- 普通正文中的行内 font/span 等格式去掉标签、保留文字；代码块中的 XML/HTML 保留。
- 删除线内容保留“已划去”状态，不能去掉删除线后让旧说法看起来重新有效。
- 对纯聊天/引用，保留显式的来源、说话角色或问题标记；没有证据时不自动判定“这是个人已验证经验”。
- 完整外层 markdown 围栏只有在确实包住全文、开闭匹配时才可作为包装处理；局部不匹配不要自动猜修复，降级并标记。
- 敏感模式只能用于筛查，不能保证完全脱敏。命中后在获准样本的派生文本中处理或暂不索引该单元，不改原文。

尤其不能只在 embedding_text 中删去敏感值，却将原值留在 Chroma documents、metadata、父上下文、预览或问答 prompt 中。

清洗后位置不能直接套原始字符串偏移。记录源跨度 source_spans；拼接多个来源范围时保留多个跨度，展示引用应对应源笔记的行号。不要再用“清洗正文一定等于某个原文连续切片”的断言验证所有情况。

### 4.3 标题和日期提供背景，不替代正文

- 路径、文件名、frontmatter title、文内标题分别保存，不相互覆盖。
- 语义明确的文件名和小节标题放入 embedding 前缀；“未命名”“笔记”“今天做了什么”和单纯日期不能作为唯一主题信息。
- 可加入少量有意义的目录上下文，例如 Python/面向对象；不把整条深目录、原始绝对路径或所有标签机械拼进前缀。
- 文件日期、frontmatter created、正文事件日期、任务 due/completed 日期分开；来源和可信度可解释。
- 源日期只有范围或无法可靠解析时，保留原始字段，不猜。mtime 单独记录，不决定事实有效性。
- 目录是来源提示；_notUsed 或 Clippings 不自动证明内容失效或有效。历史范围默认单列，是否参与当前检索由查询范围控制。

## 5. 按“局部理解单元”组块

局部单元也称父上下文。它可以恰好等于一个短小节，也可以是通用标题下的一段解释加示例；不要直接等同于整篇文件。

### 5.1 短笔记与概念对比

S19 只有数行，但两个概念放在一起才构成比较。第一版将其整篇保留，比按空行切成两个孤立半句更合适。

规则：完整的一个短主题整体保留；只有明确的多个独立主题才拆，不设硬性的最小 token 数，不为了凑长度合并别的笔记。

### 5.2 排错、操作步骤和教学例子

优先把下面内容组成一个局部单元：

```text
场景/前提/问题
  → 对应操作或示例
  → 输出/现象
  → 解释、限制或结论
```

- “前提/事实/现象/结论”往往是同一论证的不同部分，不能因为标签各占一行就拆成独立主题。
- “正确/错误/原因/解决”围绕同一例子时一起保留；若长到必须拆子块，子块必须带来源中明确的角色或关联回完整例子。
- “例如/执行/输出/结果如下”等可作为相邻关系线索，不是万能主题分类器。
- 前提可能在命令之前，解释也可能在之后，不能只固定向前取一段。
- 文首的全局条件，如版本、静态分析边界等，需要单独作为 doc_context 关联；不能靠任意附近三行覆盖整个文档约束。
- doc_context 只提取源文中明确的短范围并附来源，不用模型编造摘要。无法确定作用域时标记，操作类结果支持回看源文件。

### 5.3 日记与周记

通用模板标题保留为元数据，不为它们单独创建块，也不认定下面都是同一个主题。

先利用可靠结构：任务项、缩进列表、代码、表格、明确小标题或明显的局部示例。独立短段先分开；相关解释与代码按上一节关联。S15 中业务事项、概念解释、代码与粘贴 prompt 不应作为一个整篇父块。

没有标题时：

1. 段落、列表树和块类型切换提供候选边界。
2. 先保留短而独立的候选，不跨段机械凑满预算。
3. 短行标签可以作边界线索，但不能把每个数字/编号都当标题。
4. 没有空行的混话题长段落，按句子分割作为兜底，并保存邻接关系；不宣称规则已准确识别话题。
5. 收集这类实际检索失败后，再尝试相邻句子/段落 embedding 辅助边界判断。语义相似不保证同一单元，尤其“正确/错误”“允许/禁止”可能非常相似。

### 5.4 待办和嵌套列表

- 任务本身加子项是基本单元，保留复选状态、原始日期标记。
- 同一列表的上级条件应随下级保留，不能把子项脱离列表父项。
- 多个相互独立的任务不强行合并；查询“本月有哪些未完成任务”更适合元数据/任务列表汇总，不能只用向量 top_k 回答完整清单。
- Dataview 等动态视图不执行；从源日记索引任务。没有运行插件，不声称读到了插件实际显示的所有汇总结果。
- 步骤列表与待办列表不同：前后有依赖的一组操作应关联到同一局部上下文。

### 5.5 代码、日志与伪代码

围栏中的内容可能是 Python、Shell、XML、日志、输出、文件树或自然语言问答。围栏 info 只是提示，不能将一切当作 Python。

- 短代码与附近解释一起保留。
- 长 Python 代码：可解析时按类/函数/方法范围产生候选，保留所属代码块、限定名、签名、docstring 和必要来源说明。
- 类很长时拆方法，不将整个类强塞进一个向量；方法依赖的初始化/常量关系保留为待回读上下文，不复制所有依赖进每个块。
- 解析失败时退回行/语句边界和长度限制，并标记 code_parse_status，不替用户改缩进、补代码或把伪代码改为可执行版本。
- 在字符串、行注释和输出中出现标点，不等于代码语句边界。尽量避免把条件、错误分支、返回值说明从对应代码中切走。
- 表示关系的文字树仍有知识价值，不能因为是 text 围栏一律删除。
- 很长文件清单/附录可单独组织，不让同一来源的许多近似块占满搜索结果；这是检索分组问题，也要保留文件名精确查找能力。
- 所有代码仅作为数据解析；不 import、eval、exec 或运行源笔记代码。

### 5.6 表格和多模态缺口

表格按结构处理，不只按字符切：

- 缩写/词典/独立参数条目：一行或少量相邻条目一块，重复列标题；单条很短也允许。
- 有比较关系的少量行：一起保留，例如同一 API 的几种用法。
- 过程或跨行有依赖：保留所属表格关系，命中后回读相邻相关行，不把每行都当独立事实。
- 大单元格内部还需按语句或内部结构处理；不能无限超过模型限制。

图片、远程图、.py 嵌入或外部路径链接：只记录引用与覆盖缺口，当前不打开、OCR、下载或运行。纯链接笔记可以成为别名/跳转入口，但不能产生“目标正文已检索”的假象。后续若支持解析链接，先限于明确允许范围，处理重名、循环和缺失目标，不默认递归全库。

## 6. 子块用于检索，父上下文用于理解

```text
局部上下文单元（有源范围，不要求生成向量）
  ├─ 检索子块 A → embedding
  ├─ 检索子块 B → embedding
  └─ 检索子块 C → embedding

命中 B
  → 找到其局部单元
  → 补上必要的条件、示例角色和解释
  → 同一单元去重，控制总长度，附源位置
```

如果整个局部单元本身很短，一个块承担两种用途即可，避免无意义的多层数据。

### 参数只作为起点

| 对象 | 初始建议 | 约束 |
| --- | --- | --- |
| 检索块 | 通常 200～320 tokens | 短而完整可以远小于 200，不补无关内容 |
| embedding 总输入 | 第一轮上限 320 tokens | 包含前缀和特殊 token，并校验实际模型 max_seq_length |
| 父上下文 | 约 800～1200 tokens 的初始阅读预算 | 不是 embedding 输入；不因预算把必要条件静默截掉 |
| overlap | 不全局固定重复比例 | 先靠单元关系与必要条件补充，具体长段再单独实验 |

这里先用当前 embedding tokenizer 作统一计数，便于实验对比；它不等于 Codex 的真实 token 计费/上下文计数。数值尚未用实际样本 tokenizer 统计，不称作最佳值。

父上下文仍超预算时，应在内部继续形成局部范围，优先携带条件和相关例子。无法完整保留必要关系时输出 context_incomplete，附回看位置；不能只返回一个孤立危险命令，却标记为“完整上下文”。

在检索端，先取子块候选，再按父单元分组、去重和补上下文。父单元排序第一版可取其命中子块的最佳分数，避免简单累加分数偏向长文。复杂多来源问题保留不同来源，不把所有候选都扩成整篇。

## 7. 必要的数据字段

这些是建议的数据契约，尚未落地。先保持少量清楚的记录，不建立图数据库。

| 对象 | 必需信息 |
| --- | --- |
| 文档 | 相对路径、内容哈希、文件名、已有标题/元数据、来源类别提示、日期来源、格式/覆盖状态 |
| 结构块 | block_id、块类型、heading_path、source_spans、可读安全文本、解析状态 |
| 局部上下文 | parent_id、成员块 ID、必要全局上下文引用、上下文是否完整 |
| 检索子块 | chunk_id、parent_id、源跨度、embedding_text、token 数、明确的代码限定名/示例角色（有依据时） |
| 引用关系 | 来源块、目标原始引用、允许范围内的解析状态；链接参数也需筛查 |

说明：

- Chroma 中的 metadata 只放所需的扁平标量字段，例如 source、parent_id、kind、line_start、line_end。复杂结构与多个跨度可以存独立的本地伴随记录，不假定 Chroma 原生接受嵌套 JSON。
- Chroma documents 和父上下文均使用已经通过同一筛查规则的安全文本，不把敏感原文藏在“仅用于回读”的字段。
- 单个跨度可以定位单段原文；多个跨度组成的单元引用要保持多个范围，不把它们伪装成原文的一段连续字符串。
- chunk ID 对相同来源和相同编码文本应确定；相同内容的重复出现序号用于区分记录。为满足用户随后明确提出的频繁新增需求，v2 教程已给出同 collection 的增量同步：新 ID 编码、消失 ID 删除、仅位置/父关联变化时更新 metadata，并通过已提交快照和同步状态防止错配。模型或解析规则改变时才使用新 collection；未在真实数据库验收。
- 前缀只携带必要标题/背景，不把用户提问、生成答案或猜测的主题标签塞回文档向量。
- 对引用/生成文本的来源判断，只记录明确证据和未知状态，不因为位于普通目录就判定为个人亲测。

## 8. 工具选择与复杂度

建议下一版用成熟的 Markdown token/语法树解析器取代继续堆叠正则，例如 markdown-it-py：它提供 token 流、语法树遍历和块的源行范围。表格、frontmatter、wikilink 等扩展需要明确启用或补适配；不能声称一个 CommonMark 解析器自动完整支持 Obsidian。参见 [解析流程](https://markdown-it-py.readthedocs.io/en/latest/using.html) 和 [Token.map](https://markdown-it-py.readthedocs.io/en/latest/api/markdown_it.token.html)。

整页 HTML 可用 Python 标准库 HTMLParser 作为提取基础，但它不会替我们自动实现“正文筛选、标题层级和源范围”；需要有限的处理逻辑。参见 [Python HTMLParser](https://docs.python.org/3.12/library/html.parser.html)。

Python 代码的可选结构识别用 ast.parse，解析失败走兜底，不执行代码。参见 [Python AST](https://docs.python.org/3.12/library/ast.html)。

父子关联与上下文回取可以在自己的 Python 数据结构中实现；LlamaIndex 的层级节点和窗口节点说明了这一思路，但本阶段不需要因此安装整个框架。参见 [相关设计](https://developers.llamaindex.ai/python/framework/module_guides/loading/node_parsers/modules/)。

当前不安装新依赖。以上是实现建议，不是这些工具已在本项目安装、运行或通过真实样本的证据。

### 为什么不直接用其他方案

| 方案 | 针对实际样本的取舍 |
| --- | --- |
| 统一按字符/token 切 | 适合作对照，无法处理条件分离、HTML/CSS、长 URL 和表格关系 |
| 只按标题切 | 通用日记标题太粗，异常围栏还可能隐藏标题；长小节仍超限 |
| 每段单独一个向量 | 易实现，但教学/排错笔记的解释、正误与输出被拆散 |
| 仅靠语义相似度决定边界 | 可作辅助；不能可靠区分同主题的“允许/禁止”或“正确/错误” |
| 全部交给 LLM 改写/分块 | 引入成本、传输与改写核验，当前没有必要；也不适合直接在本机 CPU 跑大模型 |
| 结构解析 + 局部单元 + 受限上下文 | 本轮首选，能够逐项对应已经观察到的问题，剩余歧义可显式标记 |

不是禁止语义切块或 LLM 辅助。它们留给规则确实处理不好的具体案例，不作为全库第一步。

## 9. 如何验证：不需要完整标准问答题库

先验收数据处理，再看检索。以下案例都有本次读到的实际结构依据：

| 编号 | 检查场景 | 验收重点 |
| --- | --- | --- |
| T01 | 空白日记模板 | 0 个正文向量，理由明确 |
| T02 | 占位词与信息很少的短笔记 | 占位不编造知识；短事实不因长度被一律删除 |
| T03 | 短概念对比 | 比较对象与区别没有被拆散 |
| T04 | 任务树与多个日期 | 子项仍隶属父任务，日期类型不混淆 |
| T05 | 日记内多个话题 | 命中一个话题时，父上下文不整篇扩展 |
| T06 | 正确/错误代码对比 | 错误示例始终带错误角色和解释，不能单独当推荐 |
| T07 | 前提—现象—结论 | 必要条件与结论能关联回读 |
| T08 | 长代码/不规范代码 | 保留所属代码块与位置；失败降级，不执行或改源代码 |
| T09 | 实际 HTML 文档 | 可见正文可检索，CSS/布局不主导向量 |
| T10 | 长 URL 与剪藏标题冲突 | 可见文字保留，不被参数淹没；标题来源不覆盖 |
| T11 | 词典表格 | 命中条目能看到对应列名和完整释义 |
| T12 | 纯链接/截图/动态视图 | 明确未覆盖内容，不误声称已读目标或插件结果 |
| T13 | 引用对话与未决问题 | 不把历史 prompt 当指令，不把问题或撤回意见当确定答案 |
| T14 | 静态分析报告 | 回答保留静态边界，不能说已做真实台架执行 |
| T15 | 敏感字段 | 不出现在 embedding、documents、metadata、父上下文、预览和发送 prompt 中 |
| T16 | 全部可索引单元 | 来源可定位、清洗有映射、无静默截断；未索引内容都有原因 |

T15 的自动模式检查不等于全库安全认证，样本发布/发送前仍应抽查。没有必要为了测试它而在记录中复制真实值。

检索问题只需先知道一个相关位置，不需写完整标准答案。例如：

- 换个说法找短概念对比，是否找到正确笔记？
- 问某个命令为什么这样用，是否包含相应解释？
- 问某种写法哪里错，是否拿到“错误”标记和修正？
- 问任务何时完成，是否区分日记日期与完成日期？
- 问图片里才有的设置，是否如实说明当前文字范围不足？
- 问技术验证是否做过，是否保留“静态”或“未验证”的限制？

这些测试评价源证据是否完整，不代表笔记中的技术观点都已外部核实。

### 对照顺序

保持模型、样本、问题不变，分阶段增加处理层：

1. v1 作为基线，记录它在这些结构案例上的失败。
2. 增加格式识别和检索视图整理，检查噪声与覆盖变化。
3. 增加局部单元分组，检查条件和示例关系。
4. 增加父上下文回取，检查答案所需证据与无关信息量。
5. 最后才对未解决的无标题混话题段落测试语义边界，或比较模型。

每步记录块数量、被排除/降级原因、最大输入长度、来源覆盖与真实查询结果。不要同时更换模型、分块、top_k 与重排再归因。尚不知道全部相关原文的位置时，只评价已知片段命中与结果帮助程度，不声称完整召回率。

## 10. 下一步实施顺序

### 最小版本的边界

不要求一次实现表中所有增强。第一版 v2 先完成普通 Markdown 的结构与源位置、检索文本整理、解释/代码/输出关联、父子回取和异常清单；表格需能保留表头与行。敏感模式命中的单元可以先不索引、报告待核对，不必先做复杂脱敏系统。

整页 HTML 和复杂异常围栏若暂不支持，应在预览中明确标为未覆盖，不能当空文件跳过，也不能把 CSS 当正文照常建库。Python AST 可选，无法解析就保留代码关联并降级分段。链接先记录关系，不做目标解析；OCR、语义边界、重排、全库同步留在之后。这样第一步仍是一个可理解、可验收的本地程序。

### 操作顺序

1. 用户先选择一批允许处理、没有敏感值或已经脱敏的笔记副本，覆盖上面的结构类型；不要求先整理整个 Vault。
2. 下一版先只写解析/预览阶段：输出类型、局部单元、源范围、异常与覆盖缺口，暂不 embedding。
3. 通过 T01～T16 中的数据处理检查，再创建独立的 v2 快照和 Chroma collection。
4. 沿用当前 CPU 模型，分别测加载、建库、持续查询与内存；先验证检索，再接生成。
5. 用户反馈实际效果后修订规则。源笔记保持原样，不自动修复 Markdown、不删除旧笔记。增量更新只覆盖用户明确选择的来源，不自动扩大到全 Vault。

审阅后已按用户要求提供 [v2 完整教程](OBSIDIAN_RAG_V2_GUIDE.md)，包含五个参考脚本及合成/mock 验证。旧 v1 保留，项目根没有替用户创建业务脚本。用户仍需自己落地和运行；不能把文档代码或替身验证写成真实样本已通过。
